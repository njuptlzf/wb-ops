# wb-ops 省量保真度 Benchmark

> 回答一个核心质疑：**省了 token 之后，上下文失真了吗？**——shell 输出本来是完整的，压完还完整吗？
>
> 算法细节见 [ALGORITHMS.md](ALGORITHMS.md)。方法论参考同类工具（dsh-ops 等）"有界输出、可回查 spill、遏制报错循环"的原则，在其基础上增加**可量化的保真度门禁**。

## 1. 为什么确定性 benchmark 优先

用 LLM 打分评测"压缩质量"有三个问题：贵、慢、不可复现。wb-ops 的压缩是确定性算法，所以第一道评测也应是确定性的：**在夹具里预埋锚点，压缩后逐个验收**。LLM 问答评测（§4）作为第二阶段补充，而不是替代。

## 2. 评测设计与指标

夹具：带"必留信息"锚点的标准输出样本（`test/benchmark.mjs` 内程序化生成，确定性可复现）。每个锚点分两档：

| 档 | 含义 | 不达标 = 失败 |
|---|---|---|
| **critical** | 必须留在上下文：`[wb-ops]` 标记、落盘路径、`Exit Code` 行、`回看: Read offset=` 指路 | 丢一个就 FAIL（模型会失去"成败判断"或"取回原文的能力"） |
| **desired** | 最好留在上下文的具体信息行（错误/警告/堆栈） | 丢失不 FAIL，但**如实计入上下文保留率**——丢了由落盘兜底 |

五项失真检查：

1. **反捏造**：压缩结果里除标记行外，每一行都必须是原文的子串——压缩器不允许"编造"原文没有的内容
2. **行完整性**：普通路径整行保留（仅少行巨字节路径允许字节级截断，且截断行带 `…` 后缀）
3. **尾部真实性**：原文最后一个非空行必须出现在结果里（防止"尾部"是拼出来的）
4. **退出码可见性**：shell 类的 `Exit Code:` 行必须可见（失败透传、成功保底纳入尾段）
5. **预算合规**：压缩后 ≤ 预算+1200B（标记行的自留地）

基线对比：**朴素截断**（只留前 budget 字节——很多"自己截一下"的方案的实际行为）跑同一组锚点。

> v0.17 锚点扩行后：`stack-trace` 的期望信息保留率 2/6 → 6/6；总省量 86.0% → 85.6%
> （多留了 4 行堆栈帧，代价约 0.4 个百分点——这是有意付的代价，见下文）。

### 结果解读

- **压缩器零捏造**：9 个夹具、6.7 万+ 行原文，压缩结果每一行都能在原文中找到出处。这是"确定性算法"的直接红利——LLM 摘要做不到这一点
- **关键锚点 100%**：标记、落盘路径、退出码行、回看指路全部在场——模型永远知道"成功了吗"和"去哪取回原文"
- **对比朴素截断**：基线的 critical 全部为 0（尾部信息——包括退出码行——被截掉），期望信息保留 0~20%。wb-ops 在同等字节预算下期望信息保留 73%~100%
- **`read/source-800` = 0% 省**：这是**故意的**——800 行源码 < 1500 行门槛，原样透传（保真度 100%），验证"源码不裁"承诺
- **中文场景不劣化**：`cjk-log` 省字节 97.1%（字节预算在中文下优势更大：同一预算字节数≈更少汉字，但 KEY 正则中英并集保证中文错误行照样命中）

### 已解决的局限

1. ~~**关键词锚点的"上下文行"可能不在上下文里**~~ → **已根治（v0.17，2026-11-06）**
   `stack-trace` 夹具曾期望 6 条只中 2 条：`FATAL`/`ERROR` 行命中关键词被保留，但其下 4 行
   `    at Worker.run (…)` 堆栈帧不含关键词、留在落盘。现改为**锚点扩行**——严重错误行后顺带
   保留若干连续行，该夹具期望信息保留率 **2/6 → 6/6**，单测已钉死。
   配套加固：抽样改为按连续块（不打散堆栈帧）、关键行字节配额（不挤掉尾部 `Exit Code` 行）、
   锚点扩行护栏（满屏错误时不无限扩）。详见 [ROADMAP.md](ROADMAP.md)。
2. **列表中间条目按设计丢弃**：`grep/native-array` 只保前 K 条 + 总数说明，中间的报错路径需要读落盘 `.json`
3. **字节级截断路径**（≤20 行巨字节）是唯一允许"半行"的路径，截断处以 `…` 标记——夹具已验证首尾片段完整

## 4. LLM 可用性评测（第二阶段，可选）

确定性指标回答不了"模型拿到压缩输出后的**行为**是否与拿到原文时一样好"。协议：

```bash
node test/benchmark.mjs --qa    # 生成评测问答卷（每个夹具 3 个探针问题）
```

对每个夹具，把【压缩输出】与【原文】分别贴给同一个模型，问同样的 3 个探针问题（成败判断 / 错误清单 / 原文取回路径）：

| 结果 | 判定 |
|---|---|
| 两边答案一致 | ✅ 可用性保持 |
| 压缩侧答错，原文侧答对 | ❌ 失真点，记入清单（附夹具名与探针） |
| 两边都答不出 | 问题本身无效，换题 |

已知预期差异：探针答案若只存在于被省略的中间行（如某个非关键词警告的具体数值），压缩侧应回答"输出提到有警告，详情在落盘文件 <path>"——这算**正确的降级**而非失真，因为模型知道去哪取。真正要防的失真是：模型对截断后的内容**过度自信**（把不完整当完整）。标记行的"已省略 N 行"就是在对模型诚实。

## 5. 复用为回归门禁

```bash
node test/benchmark.mjs          # 表格报告；critical 丢失 / 捏造行 / 超预算 → 退出码 1
node test/benchmark.mjs --json   # 机器可读（CI 用）
```

改动压缩算法（阈值、正则、分档）后必须重跑：所有 critical 锚点、零捏造、预算合规是硬门禁；期望信息保留率如下降，需在 PR 说明取舍。

新增夹具：在 `FIXTURES` 数组加一个构造函数，给出 `critical` 正则与 `want` 锚点行即可——建议每次线上遇到"压坏了"的真实案例，先做成夹具再修算法（回归钉死）。
