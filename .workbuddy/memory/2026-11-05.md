## 14:20 修复方案评估（根因定位，不改代码）

**探测方法（可复用）**：本会话 transcript `~/.workbuddy/projects/c-Users-kingdee-work-wb-ops/<sid>.jsonl`，顶层 `type=function_call_result` 记录里 `providerData.toolResult` 就是**宿主工具结果形状**（`output` 是最终给模型的文本，`providerData` 是工具侧记录）。比在 182MB asar 里大海捞针快得多。

**根因（问题 1 Grep/Glob）**：`toolResult.content` 类型**逐工具不同**——Bash/PowerShell/Read/TaskOutput/WebFetch/MCP 是 string（extractText 命中 → 压缩生效）；**Grep 小结果是 `string[]`**（37 条路径），extractText 的数组分支只认 `{text}` 块、裸字符串数组直接 null → 通道完全失效。大结果的 content 已被宿主换成 `<persisted-output>` 摘要（约 200B）→ 低于预算 → 透传。
**宿主 persisted-output 阈值 ≈ 8KB**（"Output too large (8.3KB)"），与 mod 默认预算 8000B 重叠 → mod 工作区间被宿主抢走。

**根因（问题 2 usage）**：宿主契约 `i.usage ? core_handler_value(await i.usage(h)) : deny("$.session.usage", "the host did not wire this capability")`；`core_handler_value(t)=>{value:t}`、`deny=>({deny:...})`。宿主 session 对象自身有 `usage?.outputTokens`——**是"本轮 token 统计"味道，没有"上下文占用/窗口"语义**（未证实，但强烈怀疑）。

**风险结论**：
- 问题 1 修复安全（extractText 加 `string[]` 分支 + sink 回写数组需真机验证渲染形态 + 预算下调到宿主阈值以下留余量）。
- 问题 2 风险高：**usage 语义若非累计上下文，算出的百分比无意义 → 每轮假警报 → 污染上下文（与项目目标相反）**。建议先只做"结构探测落盘"（只写键名/类型/长度，不写正文）拿到真实形状+语义，再决定是否启用；拿到证据前保持静默是正确的。
- 长期建议：加限频形状诊断通道（`~/.workbuddy/wb-ops/debug/shapes.log`，每会话 ≤20 条，不含正文）——宿主升级改形状时能立刻定位。

## v0.12.1 修复：8MB 上限的真实性质（17:45-18:05）—— 结论与初判相反

**用户提问「8MB 上限会不会让上线后长会话出问题」→ 查证后：会，但机制与我上一轮写的不同，已修。**

### 事实采集（真实数据，非推断）
- 真实会话 transcript 体积：21.5MB(d9c8345e) / 13.4MB(f87c445e) / 10.1MB(0383a8f1) / 4.3MB(32360b9f) —— **8MB 上限会真实命中**。
- 宿主 transcript **只增不减**（实测 22MB 会话里 compactType 全是 pre-message-auto，压缩的是内存 history 不是文件）。
- 22MB 全量 `readFile+toString+split` 实测 **115ms / 内存 134MB** → 全量读完全可接受，不需尾部读。
- 沙箱 `fs.read` **无 offset/length**（只有 `{as:'text'|'base64'}`，底层 node:fs/promises.readFile）→ **无法只读尾部**；`fs.stat` 可用（size/mtimeMs）。`fs.list`/`fs.stat`/`fs.exists`/`fs.ancestors`/`fs.read`/`fs.write` 是全部文件能力。

### 关键根因：usage 归零的精确时刻 = pre-message-auto compact 之后
- f87c445e 实测：compact 摘要落盘 `isCompacted=true`（01:36:02）→ **8.2 秒后** usage 才恢复；usage 读数序列 `[0, 98564, 0, 0]`。
- usage 数据源 = `createModsUsageBinding` → `getCurrentContextUsage(session)?.totalInputTokens` → compact 后宿主快照被重置 → 短暂归零。
- **两个条件在长会话里必然同时撞上**：usage 归零窗口（compact 后 ~8s）× transcript 已 >8MB（长时间积累）→ 旧实现 fallback 永久失守 → **水位提醒彻底静默**（fail-open，故表现为"没提醒"而非报错）。
- ⚠️ 修正我上一轮的说法：旧结论「usage 恒 0、fallback 才是主力」不成立。实测 usage tokens 在会话中会涨到 306324/410003，**usage 路径是主力，fallback 只在 compact 后那 8 秒窗口起作用**——而那正是旧上限会失守的窗口。
